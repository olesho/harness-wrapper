# ADR-001: vt100 emulator selection for `pkg/screen`

**Status:** Accepted — `vt10x` chosen (2026-05-14)

## Context

The chat-extension plan layers turn detection and conversation orchestration on top of `pkg/wrapper`.
Turn detection requires interpreting a TUI harness's screen state — which means running its raw PTY
byte stream through a vt100 emulator.

`pkg/screen` will wrap exactly one emulator library. Swapping is one file, but the choice still
matters: emulator fidelity bounds how reliably we can detect prompt regions and extract assistant text.

## Candidates

| Candidate | Module | Notes |
|---|---|---|
| `vt10x` | `github.com/hinshun/vt10x` | Long-standing pure-Go emulator. Sparsely maintained but widely used (testscript, expect-style libs). |
| `charm-x-vt` | `github.com/charmbracelet/x/vt` | Newer, actively maintained as part of the Charmbracelet ecosystem. Larger dep footprint. |
| _(reserved)_ `termtest` | `github.com/ActiveState/termtest` | Has its own emulator; evaluate if the above leave fidelity gaps. |

## Evaluation methodology

Implemented in `internal/screenbench/`:

- **Corpus** ([`test/corpus/`](../testing/corpus.md)): for each of Codex and Claude Code, six canonical
  scenarios (short reply, long markdown, code block, interrupt, tool call, multi-turn). Each records
  the raw PTY byte stream plus a hand-curated `expected.txt` containing the final assistant text.
- **Bench** (`cmd/screenbench`): replays each scenario through each registered emulator; measures
  fidelity (exact match / Levenshtein / normalized distance against `expected.txt`), throughput
  (bytes/sec), and allocation delta.
- **Stability**: a settling check confirms the emulator state quiesces after the byte stream ends.

## Decision

**`pkg/screen` will wrap `github.com/hinshun/vt10x`.**

`charm-x-vt` is disqualified by a reproducible panic on real Codex output. `vt10x` is the only
candidate that survives every recording.

### Bake-off results (6/12 canonical scenarios recorded)

Recorded on a 120×40 terminal, `codex-cli 0.130.0` and Claude Code 2.1.141. `expected.txt` for each
real-harness scenario was bootstrapped from vt10x's normalized snapshot; `NDist` for vt10x is therefore
by construction 0, and `NDist` for `charm-x-vt` measures divergence from vt10x's rendering of the same
byte stream.

| Scenario | Bytes | charm-x-vt | vt10x |
|---|---:|---|---|
| codex/short-reply | 88,930 | **panic** (`index out of range [45] with length 40`) | clean · 17.8 MB/s |
| codex/long-markdown | 1,424,774 | **panic** (`index out of range [40] with length 40`) | clean · 17.8 MB/s |
| codex/code-block | 214,891 | **panic** (`index out of range [45] with length 40`) | clean · 13.4 MB/s |
| claude-code/interrupted-mid-reply | 21,717 | NDist 0.742 · 12.6 MB/s | anchor · 21.4 MB/s |
| claude-code/multi-turn | 38,032 | NDist 0.146 · 14.7 MB/s | anchor · 15.9 MB/s |
| claude-code/tool-call | 26,874 | NDist 0.636 · 13.6 MB/s | anchor · 16.9 MB/s |
| _all 6 synth scenarios_ | 84–350 | matches vt10x exactly | matches vt10x exactly |

Crash trace (all three Codex panics): reverse-index (`ESC M`) → `Screen.ScrollDown` → `InsertLine` →
`Buffer.InsertLineArea` indexing past the 40-row buffer length. The same byte streams replay through
vt10x without incident.

### Criteria, weighted (priority order)

1. **Safety on real harness output** — `charm-x-vt` fails outright; `vt10x` passes.
2. **Stability across scenarios** — `vt10x` runs every recording cleanly.
3. **Throughput** — `vt10x` consistently 13–22 MB/s on real bytes; comfortable margin for streaming.
4. **Dependency footprint** — `vt10x` brings 5 transitive deps; `charm-x-vt` brings ~10.
5. **Maintenance activity** — `vt10x` is sparsely maintained but the import surface we use (`Write`,
   `String`, `Cursor`, `Size`) is stable. `charm-x-vt` is more active, but the active-development churn
   is what's producing the panic.

## Consequences

`pkg/screen` wraps the winner behind a small interface (`Write`, `Snapshot`, `Cursor`, `Size`; see
[Screen](../screen.md)). If the chosen emulator's fidelity is below acceptable on a given harness, the
affected [adapter](../turns.md) should bias toward reading the harness's own
[JSONL transcript](../transcript.md) for turn text and use the screen only for liveness signal.

If no candidate clears the fidelity bar on critical scenarios, options are: add the `termtest`
candidate and re-run; pre-filter byte streams (resolve alternate-screen mode separately); or layer a
thin screen-region heuristic on top of a weaker emulator.
