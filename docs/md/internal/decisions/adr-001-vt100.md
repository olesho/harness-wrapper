# ADR-001: vt100 emulator selection for `pkg/screen`

**Status:** Accepted (2026-05-14) — `vt10x` chosen

**Intent:** principle 1, *the screen is a contract we don't own*, and principle 4, *prefer the
harness's own record* ([INTENT](../../../../INTENT.md#design-principles)).

## Context

Turn detection and conversation orchestration are layered on top of `pkg/wrapper`. Turn detection
requires interpreting a TUI harness's screen state — which means running its raw PTY byte stream
through a vt100 emulator.

`pkg/screen` wraps exactly one emulator library. Swapping is one file, but the choice still matters:
emulator fidelity bounds how reliably we can detect prompt regions and extract assistant text.

## Decision

**`pkg/screen` wraps `github.com/hinshun/vt10x`**, behind a small interface (`Write`, `Snapshot`,
`Cursor`, `Size`; see [Screen](../screen.md)).

The choice was made by bake-off on recorded sessions, not by feature comparison. `charm-x-vt` is
disqualified by a reproducible panic on real Codex output; `vt10x` is the only candidate that
survives every recording.

## Alternatives

| Candidate | Module | Notes | Outcome |
|---|---|---|---|
| `vt10x` | `github.com/hinshun/vt10x` | Long-standing pure-Go emulator. Sparsely maintained but widely used (testscript, expect-style libs). | **Chosen** |
| `charm-x-vt` | `github.com/charmbracelet/x/vt` | Newer, actively maintained as part of the Charmbracelet ecosystem. Larger dep footprint. | Rejected — panics on real Codex output |
| `termtest` | `github.com/ActiveState/termtest` | Has its own emulator. | Reserved — evaluate if the above leave fidelity gaps |

Criteria, in priority order:

1. **Safety on real harness output** — `charm-x-vt` fails outright; `vt10x` passes.
2. **Stability across scenarios** — `vt10x` runs every recording cleanly.
3. **Throughput** — `vt10x` consistently 13–22 MB/s on real bytes; comfortable margin for streaming.
4. **Dependency footprint** — `vt10x` brings 5 transitive deps; `charm-x-vt` brings ~10.
5. **Maintenance activity** — `vt10x` is sparsely maintained but the import surface we use (`Write`,
   `String`, `Cursor`, `Size`) is stable. `charm-x-vt` is more active, but the active-development
   churn is what's producing the panic.

## Evidence

### Method

Implemented in `internal/screenbench/`:

- **Corpus** ([`test/corpus/`](../testing/corpus.md)): for each of Codex and Claude Code, six canonical
  scenarios (short reply, long markdown, code block, interrupt, tool call, multi-turn). Each records
  the raw PTY byte stream plus an `expected.txt` holding the final assistant text.
- **Bench** (`cmd/screenbench`): replays each scenario through each registered emulator; measures
  fidelity (exact match / Levenshtein / normalized distance against `expected.txt`), throughput
  (bytes/sec), and allocation delta.
- **Stability**: a settling check confirms the emulator state quiesces after the byte stream ends.

### Bake-off results (6/12 canonical scenarios recorded)

Recorded on a 120×40 terminal, `codex-cli 0.130.0` and Claude Code 2.1.141.

| Scenario | Bytes | charm-x-vt | vt10x |
|---|---:|---|---|
| codex/short-reply | 88,930 | **panic** (`index out of range [45] with length 40`) | clean · 17.8 MB/s |
| codex/long-markdown | 1,424,774 | **panic** (`index out of range [40] with length 40`) | clean · 17.8 MB/s |
| codex/code-block | 214,891 | **panic** (`index out of range [45] with length 40`) | clean · 13.4 MB/s |
| claude-code/interrupted-mid-reply | 21,717 | NDist 0.742 · 12.6 MB/s | anchor · 21.4 MB/s |
| claude-code/multi-turn | 38,032 | NDist 0.146 · 14.7 MB/s | anchor · 15.9 MB/s |
| claude-code/tool-call | 26,874 | NDist 0.636 · 13.6 MB/s | anchor · 16.9 MB/s |
| _all 6 synth scenarios_ | 84–350 | matches vt10x exactly | matches vt10x exactly |

Crash trace (all three Codex panics): reverse-index (`ESC M`) → `Screen.ScrollDown` → `InsertLine` →
`Buffer.InsertLineArea` indexing past the 40-row buffer length. The same byte streams replay through
vt10x without incident.

**How to read the fidelity column.** The bake-off scored fidelity against an `expected.txt`
bootstrapped from vt10x's normalized snapshot, so vt10x's `NDist` is 0 by construction (shown as
*anchor*) and `charm-x-vt`'s `NDist` measures divergence from vt10x's rendering of the same byte
stream — not absolute correctness. The decision rests on the panics, not on that column.

The corpus was re-baked on 2026-06-26 (codex 0.142.2) and its `expected.txt` files now hold
hand-curated final assistant text. The byte counts and distances above are the evidence the decision
was made on, not a description of today's corpus; see [Corpus](../testing/corpus.md) and the
[TS addendum](adr-001-vt100-ts.md) for the current fidelity gates.

## Consequences

- `pkg/screen` wraps the winner behind the small interface above, so a later swap stays one file.
- If the chosen emulator's fidelity is below acceptable on a given harness, the affected
  [adapter](../turns.md) should bias toward reading the harness's own
  [JSONL transcript](../transcript.md) for turn text and use the screen only for liveness signal.
- If no candidate clears the fidelity bar on critical scenarios, options are: add the `termtest`
  candidate and re-run; pre-filter byte streams (resolve alternate-screen mode separately); or layer
  a thin screen-region heuristic on top of a weaker emulator.
